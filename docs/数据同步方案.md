# FitTrack 数据同步方案（待定）

> **状态：未实施。** 本文只记录选型分析，供以后决定时直接捡起来，不代表已排期。
> 现状：跨设备同步靠「导出 JSON / 导入 JSON」手工搬，见 `docs/使用手册.md` 第 5 节。

## 1. 问题本质

`localStorage` 是**按「浏览器 + 设备」隔离**的。同一个网址，电脑上的 Chrome 和手机上的 Chrome 是两个完全独立的存储，互相不可见。Mac 版更彻底 —— 数据是 `~/Library/Application Support/FitTrack/` 下的本地文件。

所以跨设备同步**不是「缺一个同步按钮」，是当前架构下做不到**：两端从不见面。要同步，中间必须有一个第三方转手，或者两端能直接对话（局域网 P2P，代价高、只限同一 Wi-Fi，不作为同步方案）。

## 2. 有利条件

两端的 JSON 格式已经**逐字节兼容**（`encodeJSON` 手写序列化器对齐 Foundation，`models.test.ts` 钉住）。所以同步本质上就是**搬运那一份 `AppData` JSON**：

- 不需要字段映射
- 不需要引入数据库
- Mac 的 `AppData` 和网页的 `AppData` 是同一份结构

## 3. 候选方案

| 方案 | 做法 | 成本 | 关键卡点 |
|---|---|---|---|
| **A. 把现有搬运做顺** | 修「导入不恢复设置」+ 加二维码/链接导入 | 小 | 仍手动；整包覆盖会丢数据 |
| **B. GitHub Gist 当同步盘** | 两端存 fine-grained PAT（只给 Gists 权限）+ gist id，点「同步」拉/推 | 中 | 要处理冲突；token 存本地 |
| **C. 自建 Cloudflare Worker** | 一个 `POST /sync`，按「同步码」存取一份 JSON | 中高 | 多一个要维护的服务；数据落在第三方 |
| **D. 网盘 WebDAV** | 坚果云 / Nextcloud 等 | — | **浏览器端走不通**：这类服务不返 CORS 头，`fetch` 直接被拦。只有 Mac 端能做 |

### A. 把现有搬运做顺

两件事，都能独立做：

1. **修导入范围**（`CLAUDE.md` 里已列为下一步）：当前 `Importer` 只恢复 `workouts` + `bodyMetrics` + `chat`，导出的文件里带着 `profile` / `goal` / `bigThree` / `coachNotes` 但导入时被忽略。改成可选的「全量恢复」模式，换设备就不用重填资料了。
2. **二维码 / 链接导入**：把 JSON 压缩后塞进 URL hash，手机扫一下打开即导入。纯前端、零后端。

### B. GitHub Gist 当同步盘

可行性来自两点：GitHub API **返回 CORS 头**（浏览器能直连，手机一样）；已有的账号 token 就带 `gist` 权限。

- 两端各配一次：一个 fine-grained PAT（**只勾 Gists 权限**，不要用全权限 token）+ gist id
- 点「同步」→ 拉云端 / 推本地 / 显示两边时间戳让用户选
- 数据只存在**私有 gist** 里，只有 token 持有者能读
- 风险面：PAT 存在 `localStorage`（网页版）和 Keychain（Mac 版）。网页版这一侧的暴露面与现有的 DeepSeek Key 相同 —— 都是自己 origin 下的本地存储

### C. 自建 Cloudflare Worker + KV

体验最好：电脑和手机各填一次「同步码」，之后点同步即可，不用碰 GitHub。

代价是要自己写并维护一个小服务（CORS、并发写、过期清理），且数据要经过第三方。免费额度对个人用量足够。

## 4. 四条设计规则（不管选哪个）

1. **本地永远是唯一事实来源**，云端只做搬运。断网、没配同步时 App 必须照常可用 —— 不能变成联网才能开。
2. **同步是显式动作**，不做后台自动轮询。没有版本向量的自动同步，一定会静默丢数据。
3. **合并分两类**，这是避免「手机记了三次训练，一同步全没了」的关键：
   - `workouts` / `bodyMetrics` / `plannedWorkouts` / `dietLogs`：每条都有 UUID 且只增不改 → **按 id 取并集**
   - `profile` / `goal` / `bigThree` / `coachNotes`：单值配置 → **二选一**（时间戳新者胜，或弹窗让用户选）

   这个混合策略能消掉九成冲突，明显优于整包覆盖。
4. **同步前自动存一份带时间戳的本地快照**，出问题能回滚。

## 5. 推荐路径

先做 **A 的「修导入范围」**：成本最低、立刻解决「换设备要重填资料」这个真痛点，而且是任何同步方案的前置 —— 同步失败时兜底的仍是导入导出。

之后再决定是否上 B。若 A 做完仍觉得手动搬太烦，B 是当前架构下性价比最高的选择（零新增基础设施 + 复用已有账号 + 浏览器可直连）。

## 6. 如果做 B，大致要动的地方

两端都要改，因为 Mac 上也想同步。

**网页版**

- 新增 `src/sync.ts`：GitHub Gist 的读写（GET/PATCH `https://api.github.com/gists/{id}`）、合并逻辑、快照
- `src/store.ts`：加 `lastSyncedAt` 与合并入口
- `src/screens/Settings.tsx`：加「同步」分组（PAT / gist id / 手动拉取 / 手动推送）

**Mac 版**

- 新增 `Sources/FitTrack/SyncService.swift`：同一套 Gist 读写（`URLSession`），与网页版共用同一份 JSON 编解码
- `Views.swift` 的 `ProfileView`：加同样的同步分组
- Keychain 存 PAT（复用 `AICredentials` 的模式）

**共同**

- 合并函数必须在两端行为一致 —— 参考现有做法，可以再开一个 `scripts/oracle/sync/` 用 Swift 跑一遍边界场景输出期望值，让 `sync.test.ts` 逐值比对（和 `patch.json` 同一套路）
