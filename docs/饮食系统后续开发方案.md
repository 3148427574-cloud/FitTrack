# FitTrack 饮食系统后续开发方案

> **状态：规划中，尚未实施。**
>
> 本文描述饮食系统的后续开发顺序、数据契约、算法口径和验收门槛。文中“当前”表示仓库现状，“规划”表示尚未完成的能力；不得把规划项当作已上线功能。

## 1. 文档目标

本方案用于把现有“每日目标 + 今日记录”能力演进为可恢复、可复核、可跨端验证的饮食记录系统，重点解决：

1. 备份不能完整恢复饮食数据的问题；
2. 只看单日、无法观察趋势的问题；
3. 记录饮食步骤多、历史条目不能编辑的问题；
4. 图片估算的可靠性、安全性和 Apple 端能力缺口；
5. 将来跨设备同步所需的版本、更新时间和删除语义。

本文不提供工期估算。开发顺序以数据安全和可回滚为第一约束，而不是以界面可见度排序。

## 2. 当前基线

### 2.1 架构与存储

- Apple 端为 SwiftUI，macOS 与 iOS 共用 `Sources/FitTrack/`；macOS 使用本地 JSON 文件。
- Web 端为 React + TypeScript + Vite，使用浏览器 `localStorage`。
- 当前没有业务后端。两端 `AppData` JSON 字段保持兼容，并以 Swift/Foundation 编码结果作为跨端 oracle。
- iOS target 当前只保证能构建，尚未真机运行；涉及相册、网络、后台切换的行为必须补真机验收。

### 2.2 已实现的饮食能力

当前已经实现，后续改造必须保持：

- Mifflin-St Jeor BMR/TDEE；
- 每日盈余/缺口按 `abs(weeklyTargetDeltaKG * 7700 / 7)` 计算，并限制在 `150...700 kcal`；维持目标不加减热量；
- 目标热量下限 `1200 kcal`；
- 蛋白质：增肌/减脂 `2.0 g/kg`，维持 `1.6 g/kg`；脂肪 `0.9 g/kg`，剩余热量分配给碳水；
- 今日摄入热量和宏量营养汇总、动态建议；
- `DietLog` 保存记录时营养快照，旧记录缺快照时按食物名称和克数回查食物库；
- 删除饮食日志；
- Web 图片识别：OpenAI-compatible Vision，读取 `VITE_VISION_API_KEY`、`VITE_VISION_API_URL`、`VITE_VISION_MODEL`，图片最长边压到 1280、JPEG 质量 0.82，用户编辑确认后保存日志，不持久化原图；
- Mac 端没有图片识别。

当前 `DietLog` 字段为：

```text
id / date / foodName / amountG
+ optional foodId / kcal / protein / carb / fat / source / imageName
```

当前导入只恢复 `workouts`、`bodyMetrics`、`chat`，不会恢复 `dietLogs`、`foods`、`plannedWorkouts`、资料设置等完整 `AppData`。这是 P0 阻断项。

### 2.3 必须遵守的兼容约束

1. Swift `Codable` 结构新增持久化字段必须是 optional，或实现显式兼容解码并提供默认值；否则旧 JSON 可能整体解码失败。
2. Web 归一化逻辑与 Swift 解码迁移必须同时设计，不能只让一端“能读”。
3. 日期按设备当前时区的本地自然日统计；持久化仍使用 ISO8601 时间点。不得把 UTC 日期字符串直接当成本地日键。
4. 历史 `DietLog` 的营养快照是事实记录。食物库后续编辑不得反向改变历史摄入。
5. 外部识别结果永远是估算，必须经用户确认后才能写入正式日志。

## 3. 原则与非目标

### 3.1 设计原则

- **先保数据，再加能力**：完整导入、备份和迁移测试先于自适应、快捷记录与同步。
- **本地优先**：断网时除图片识别外，记录、统计、编辑、导入导出均可用。
- **建议而非自动处方**：趋势算法只产生可解释建议，用户明确确认后才改变热量校准；不得自动改目标类型、目标体重或每周目标变化。
- **同算法、同口径**：纯函数在 TypeScript 与 Swift 逐值一致，用共享 fixture/oracle 防漂移。
- **缺失不是零**：未记录日不参与摄入均值、宏量达标率和完整日判断，图表显示缺口。
- **最少持久化**：最近使用可从日志推导；原图、临时预览、识别请求体不落盘。
- **可追溯**：所有热量校准建议保留依据窗口、结果、状态和用户决定。

### 3.2 非目标

- 不把 FitTrack 定位为医疗器械、疾病诊断或治疗工具。
- 不承诺仅凭照片精确测量份量、烹调用油或热量。
- 不在本方案中重复决定完整跨设备同步供应商和部署选型；详见 [`docs/数据同步方案.md`](./数据同步方案.md)。
- 不在第一版 Apple 图片识别中加入 iOS 相机拍摄或相机权限。
- 不建设通用营养内容社区、餐厅菜单数据库、条码供应链或支付系统。
- 不为所有普通本地功能滥加 feature flag；功能开关仅用于外部视觉服务等高风险能力。

## 4. 总体路线图与优先级

| 顺序 | 优先级 | 阶段 | 依赖与理由 |
|---|---|---|---|
| 1 | P0 | 数据可靠性与完整恢复 | 所有后续模型变更的安全底座 |
| 2 | P1 | 7 日体重趋势与自适应热量校准 | 先建立保守、可解释、可测试的反馈闭环 |
| 3 | P1 | 饮食周视图 | 复用趋势和日汇总纯函数，验证数据质量 |
| 4 | P1 | 快捷记录 | 增加餐次、常用餐、复制昨日、最近使用、自定义食物、日志编辑 |
| 5 | P2 | 视觉识别增强 | 完善多食物、范围、置信度和食物库匹配 |
| 6 | P2 | API 代理与安全 | 公开部署前必须完成，移除生产浏览器秘密 |
| 7 | P2 | Mac/iOS 图片识别 | 复用代理 DTO；iOS 先相册、不含相机 |
| 8 | P3 | 跨设备同步 | 以前述版本、时间戳、删除语义为前置 |

P1 内推荐严格按“趋势算法 → 周视图 → 快捷记录”实施；快捷记录引入编辑和删除语义后，再进入同步设计。

## 5. P0：数据可靠性与完整恢复

### 5.1 用户故事

- 作为用户，我能导出一份备份，并在新设备完整恢复饮食日志、食物库和设置。
- 作为旧版本用户，我升级后原有 JSON/localStorage 不丢失。
- 作为开发者，我能知道导入是“全量替换”还是“合并”，并在覆盖前自动备份。

### 5.2 功能范围

- 为 `AppData` 增加 optional `schemaVersion`、`createdAt`、`updatedAt`。
- 导出包含完整 `AppData` 与聊天；明确导出版本。
- JSON 导入提供：
  - **完整恢复**：先创建本地快照，再替换全部可识别字段；
  - **安全合并**：集合按 id 合并，单值配置明确展示保留本地或使用备份。
- 完整恢复至少覆盖 `profile`、`goal`、`workouts`、`plannedWorkouts`、`bodyMetrics`、`foods`、`exercises`、`dietLogs`、`bigThree`、`coachNotes`、未来的 `mealTemplates` 与自适应状态。
- 导入前展示条目计数，导入后展示实际新增、更新、忽略数量。

### 5.3 模型与迁移

- `schemaVersion` 缺失视为 v1；迁移函数按版本逐级执行且幂等。
- 根级时间戳仅描述整包创建/修改，不替代实体级 `updatedAt`。
- 旧 `DietLog` 缺营养快照时保持现有回查逻辑；导入不能擅自写入“0 快照”。
- 无效 UUID、日期或负营养值应报告并跳过对应条目；不能因一条坏数据静默清空整包。

### 5.4 UI 与 Store/服务改造

**Web**：`ImportExport.tsx` 增加模式选择、预览摘要、覆盖确认、失败明细和备份下载；`store.ts` 提供原子 `replace/merge/migrate` 入口。

**Swift**：`Views.swift` 中导入页增加同等确认流程；`Importer.swift` 解析完整结构；`AppStore.swift` 在替换前把当前 JSON 复制为带时间戳的本地备份，并继续采用原子写入。

导入逻辑应从视图抽成纯解析/迁移/合并层；UI 不直接拼接数组。

### 5.5 测试

- v1 旧备份、当前备份、缺 optional 字段、未知未来字段、坏单条记录、重复 id；
- Mac 导出 → Web 恢复、Web 导出 → Mac 恢复；
- 完整恢复后 `dietLogs` 数量、id、日期、营养快照逐值一致；
- 导入失败不改变当前数据；覆盖前备份可重新导入。

### 5.6 验收标准

- 新设备能通过一份 JSON 恢复全部饮食日志、食物库、设置及其他 `AppData` 集合；
- 旧数据文件可读，迁移后重新导出仍能被两端读取；
- 重复执行同一合并导入不会重复追加相同 id；
- 任一失败路径不会用空数据覆盖有效数据；
- UI 明确标注“完整恢复会替换本地配置”。

### 5.7 边界条件

空备份、超大备份、重复 id、同 id 内容冲突、跨时区导入、缺食物库但日志带快照、日志既无快照又找不到食物。最后一种应保留日志并标为“营养信息缺失”，不能按 0 参与完整日统计。

## 6. P1：7 日体重趋势与自适应热量校准

### 6.1 用户故事与范围

- 用户能看到经过平滑的体重趋势，而不是被单日水分波动误导。
- 增肌/减脂用户在数据充足且连续偏离目标时收到小幅热量调整建议。
- 建议必须显示依据、幅度、风险提示，并由用户确认；维持状态不做自动校准建议。

### 6.2 明确算法

#### 6.2.1 数据预处理

1. 以设备当前时区将 `BodyMetric.date` 归入本地自然日。
2. 同一天有多条体重时，只取**当天时间最晚的一条有效体重**。
3. 有效体重必须是有限正数；建议沿用资料合理范围校验，明显异常值不进入趋势并提示修正。
4. 形成按自然日升序的稀疏序列；缺失日不补 0、不前向填充。

#### 6.2.2 评估资格

- 从最早窗口首日到最新窗口末日至少覆盖 14 个自然日；
- 前后各取 7 个自然日窗口，每个窗口至少有 4 个有效日点；
- 两个窗口不重叠；
- `days` 为前窗口平均日期与后窗口平均日期之间的实际天数，必须大于 0，避免把稀疏数据强行按 7 天计算。

每个窗口的平均体重是窗口内有效日值的算术平均。图表可展示每日 7 日移动平均：以当天为末端，回看 7 个自然日，有效点不足 4 个则该日趋势值缺失。

#### 6.2.3 实际变化与方向

```text
actualWeeklyDelta = (latestAvg - earliestAvg) / days * 7
```

目标有方向：

- `bulk`：`targetSignedDelta = +abs(weeklyTargetDeltaKG)`；
- `cut`：`targetSignedDelta = -abs(weeklyTargetDeltaKG)`；
- `maintain`：不产生热量调整建议，只展示趋势。

```text
deviation = actualWeeklyDelta - targetSignedDelta
```

建议阈值为 `abs(deviation) >= 0.15 kg/week`。低于阈值视为可接受噪声。

#### 6.2.4 连续评估与调整

- 最多每 7 个自然日完成一次正式评估；滚动查看可以实时计算趋势，但不能每天累加一次“偏离”。
- 只有连续两次合格评估均超过阈值，且偏离方向一致，才创建待确认建议；中间出现数据不足、回到阈值内或方向反转，连续计数重置。
- 热量方向：
  - 实际体重变化比目标更低（`deviation < 0`）时，建议增加热量；
  - 实际体重变化比目标更高（`deviation > 0`）时，建议减少热量。
- 每次建议固定为保守档位 `100 kcal`；只有 `abs(deviation) >= 0.30 kg/week` 且两次同向偏离时可建议 `150 kcal`。
- 保存的是相对基础策略的累计 `calorieAdjustmentKcal`。累计绝对值不得超过 `700 kcal`；最终目标热量仍不得低于 `1200 kcal`。
- 若本次可用余量小于 100 kcal，不再建议继续调整。
- 用户可接受、忽略或稍后处理。只有接受后更新校准值；**不得自动修改** `goal.type`、`targetWeightKG` 或 `weeklyTargetDeltaKG`。
- 目标类型或每周目标变化被用户修改时，清空连续偏离状态；历史评估保留但标注其目标快照。

> 体重短期受水分、糖原、盐摄入、月经周期、消化道内容物和称重条件影响。UI 必须提示趋势是估算，建议先保持相近称重条件，不因一次异常读数调整饮食。

### 6.3 状态模型

每次正式评估应保存输入摘要和决策状态，便于解释、跨端一致和防重复：

- 窗口起止、两个平均值、有效点数、`days`；
- 目标类型与目标周变化快照；
- 实际周变化、偏差、建议 kcal；
- `insufficient/withinRange/deviating/suggested/accepted/dismissed` 状态；
- 创建、决定时间；
- 连续同向偏离次数可由最近评估推导，也可在根状态缓存，但评估历史是事实来源。

`accepted` 后将建议值叠加到 `DietCalibration.currentAdjustmentKcal`，并记录 `appliedAdjustmentKcal`。重算历史时不得重复应用同一评估。

### 6.4 Web/Swift UI

- 饮食页增加“体重趋势与校准”卡片：7 日趋势、样本充足性、最近评估、当前校准值。
- 待确认建议展示：“当前趋势、目标趋势、连续偏离次数、建议 +/−100 或 150 kcal、调整后目标热量”。
- 提供“接受”“暂不调整”；不使用危险性强的“一键自动优化”。
- 维持状态只显示“维持目标暂不启用热量校准”。

### 6.5 Store/服务改造

- `engine.ts` / `Engine.swift` 增加纯函数：按日去重、移动平均、窗口资格、评估、建议幅度。
- Store 提供 `recordEvaluation`、`acceptCalibrationSuggestion`、`dismissSuggestion`，保证同一评估幂等。
- `DietPlanner.targets` 接受校准值，先算现有基础策略，再叠加校准并执行总调整上限与 1200 下限。

### 6.6 测试与验收

关键用例：同日多条取最后；每窗 3 点不评估、4 点可评估；刚好 14 日；跨夏令时；增肌和减脂方向；阈值 0.149/0.150；连续两次同向；方向反转重置；维持不建议；累计达到 700；1200 下限；重复接受幂等。

验收标准：

- 两端对同一 fixture 的窗口、平均值、周变化、状态和建议 kcal 逐值一致；
- 数据不足时只说明缺什么，不显示方向性建议；
- 单次评估、单日异常或维持目标均不会修改热量；
- 接受前目标不变，接受后才应用，且可从记录解释变化来源。

### 6.7 迁移兼容

旧数据没有评估状态时视为空；校准值默认为 0。所有 Swift 新字段 optional，或通过自定义 `init(from:)` 提供默认空数组/0。旧目标公式结果必须在校准值为 0 时逐值不变。

## 7. P1：饮食周视图

### 7.1 用户故事与范围

用户可以按本地周或滚动最近 7 个自然日查看摄入完整度、平均值、宏量达标、体重趋势和目标热量变化。第一版建议默认“最近 7 日”，并允许前后切换 7 日区间；所有日期按本地自然日。

### 7.2 指标口径

| 指标 | 计算规则 |
|---|---|
| 7 日平均热量 | 仅对“完整记录天”的总热量求平均；无完整日显示“暂无数据”，不能除以 7 |
| 宏量达标天数 | 分别统计完整日中蛋白/碳水/脂肪落在目标容差内的天数，显示 `达标天/完整天` |
| 完整记录天 | 至少存在一条有效饮食日志，且用户显式标记“今日记录完成”；在引入显式标记前只能显示“有记录天”，不得冒充完整日 |
| 体重趋势 | 使用第 6 节同一 7 日移动平均；有效点不足则断线 |
| 热量目标变化 | 使用每日生效目标快照或由目标历史计算；不能拿当前目标回填过去所有日期 |

建议宏量容差首版为：蛋白质达到目标的 90% 及以上；碳水、脂肪在目标的 80%～120%。该口径必须在 UI 可见并集中定义，后续调整需版本化。热量可额外显示目标的 90%～110% 区间，但不替代宏量达标定义。

为支持“完整记录天”和历史目标，应增加轻量 `DietDayStatus`，以及在日志完成当天保存 `targetSnapshot`。若暂不增加目标快照，则周视图必须明确“按当前目标回算”，且不得展示“热量目标变化”图；推荐直接保存快照。

### 7.3 图表建议

- 每日热量：柱状图；完整日实心、有记录未完成日斜纹/浅色、缺失日留空；叠加目标热量折线。
- 宏量：三组达标天数进度条或小型分组柱，不建议把四条不同量纲折线挤在一起。
- 体重：原始日点淡色，7 日移动平均主线；缺失区间断线。
- 校准历史：目标热量阶梯线或变更标记，tooltip 显示接受的评估 id 和幅度。

### 7.4 模型、UI、Store 与边界

- 新增 optional `dietDayStatuses`；按 `localDate` 唯一，Store 写入时覆盖同日状态并更新时间。
- Web 新建周视图组件，复用现有图表基础组件；Swift 使用 Charts（系统框架）前先确认当前 target 可用，不引入未声明依赖。
- 日期边界使用 `Calendar.current.startOfDay` / 本地年月日构造，不用固定 24 小时毫秒跨日。
- 日志编辑、删除后周统计即时重算；已标完整但日志全部删除时自动撤销完整状态并提示。

测试覆盖跨月/年、夏令时、0 条日志、仅一条日志、营养缺失、目标中途变化、完整状态撤销。验收要求缺失日视觉上与 0 摄入明确不同，所有分母可从界面读出。

## 8. P1：快捷记录与日志编辑

### 8.1 用户故事

- 用户可给记录标注早餐、午餐、晚餐、加餐；
- 可从最近使用或常用餐快速添加；
- 可复制昨日记录，但生成今天的新记录；
- 可维护自定义食物；
- 可编辑已保存日志的日期、餐次、名称、克数和营养快照。

### 8.2 模型方案

`mealType` 枚举固定跨端原始值：`breakfast`、`lunch`、`dinner`、`snack`。旧日志缺失时 UI 归为“未分类”，不要迁移时猜测餐次。

`MealTemplate` 保存模板名称及 `items`；item 保存食物引用与模板快照，避免食物被删后模板完全失效。最近食物**不持久化**，由非删除日志按 `date` 倒序去重推导，建议取最近 20 个名称/foodId。

复制昨日规则：

- 按本地自然日找到前一天的有效日志；
- 每条生成新 UUID、新的目标日期/时间；
- 保留 `foodName`、`amountG`、`foodId`、营养快照、`mealType` 和来源语义；
- `source` 建议设为 `copied`，不伪装为 `manual` 或 `image`；
- 不复制原始 `id`、`createdAt`、`updatedAt`、`deletedAt`、`imageName`；图片名与今日记录无关；
- 保存前展示条目和合计，用户确认后批量原子写入。

自定义食物编辑只影响未来按食物库计算的新日志；历史日志使用原营养快照，不回写。删除正在被模板引用的食物时，模板仍可使用自身快照，并提示引用已失联。

### 8.3 日志编辑

编辑应覆盖：日期/时间、餐次、食物名、克数、kcal/P/C/F。若用户选择食物库条目并修改克数，则按该食物每 100g 值重算快照；若手动改任一营养值，则保存用户确认后的快照。编辑必须更新 `updatedAt`，id 保持不变。

删除在 P1 本地阶段可继续物理删除；但进入 P3 同步前必须改为墓碑/`deletedAt`，否则其他设备会把被删记录重新合并回来。

### 8.4 UI 与 Store

**Web**：饮食页顶部提供餐次切换、最近使用、常用餐、复制昨日；食物库提供新增/编辑自定义食物；日志行增加编辑入口。复杂模板管理建议新建独立组件，而非继续膨胀 `Diet.tsx`。

**Swift**：`Views.swift` 已很大，新增 `DietView.swift`、`DietLogEditorView.swift`、`MealTemplateView.swift` 等文件；仅迁移饮食相关视图，不做无关页面重构。

Store 增加批量原子添加、更新日志、模板 CRUD、自定义食物 CRUD。模板应用和复制昨日使用纯函数先生成草稿，再一次 commit/save，避免只写入一半。

### 8.5 测试、验收与兼容

- 旧日志无 `mealType` 正常显示；模板食物被删仍可创建快照日志；
- 复制昨日全部新 id、日期正确、营养合计一致且不带图片名；
- 编辑食物库不改变历史汇总；编辑日志会改变对应日汇总；
- 最近使用排序稳定、同一食物去重、不需要额外持久化；
- 批量保存失败不产生部分记录。

验收标准是上述五条在两端均成立，且模板/自定义食物经导出导入后完整恢复。

## 9. P2：视觉识别增强

### 9.1 范围与产品边界

识别一张图中的多个食物，返回可编辑条目、估算范围、误差原因、置信度及可选食物库匹配。图片不能可靠得知隐藏用油、配料、烹饪吸水率或真实重量，因此不能宣称“精确测热量”。

### 9.2 结果 schema 与校验

服务端/客户端都必须校验：

- `items` 为非空且有限长度数组；
- 名称非空并限制长度；
- 所有数值有限且非负；
- `confidence` 必须满足 `0 <= confidence <= 1`。当前 Web 只校验非负，必须补 `<= 1`；UI 不得仅通过 `min(1, value)` 掩盖坏数据；
- 区间必须 `min <= estimate <= max`；
- 宏量和 kcal 允许估算不满足严格 4/4/9 等式，但偏差过大应提示复核。

建议 DTO：

```json
{
  "requestId": "rec_01H...",
  "items": [
    {
      "name": "米饭",
      "amountG": 180,
      "amountRangeG": { "min": 140, "max": 230 },
      "kcal": 209,
      "kcalRange": { "min": 160, "max": 290 },
      "protein": 4.7,
      "carb": 46.6,
      "fat": 0.5,
      "confidence": 0.72,
      "uncertaintyReasons": ["缺少尺寸参照", "碗底不可见"],
      "matchedFoodId": "optional-uuid"
    }
  ],
  "warnings": ["烹调用油无法从照片准确判断"]
}
```

### 9.3 食物库匹配与低置信度

- 先规范化名称（空白、全半角、常见括号），再做完全匹配；模糊匹配只作为候选，不自动绑定。
- 匹配后可用食物库每 100g 数据计算第二组参考值，向用户展示“模型估算”和“食物库换算”，由用户选择，不静默覆盖。
- `confidence < 0.5` 视为低置信度：高亮、默认要求手动确认份量和名称，不能一键全选保存。
- `0.5...0.8` 显示普通估算提示；`>= 0.8` 仍需确认，不代表准确。
- 用户可删除误识别项、拆分/合并项、添加漏识别食物。

### 9.4 数据流、错误与验收

```text
选图 → 客户端校验/压缩 → 上传代理 → 代理调用 Vision
→ schema 校验与标准化 → 客户端展示草稿/范围/警告
→ 用户编辑并确认 → 写入 DietLog 营养快照 → 丢弃图片与临时响应
```

错误分为：不支持格式、图片过大、压缩失败、离线、超时、限流、供应商认证失败、供应商 schema 错误、无可识别食物。所有错误保留当前正式日志，不自动重试付费请求；用户可主动重试。

验收：单食物、多食物、空盘、遮挡、混合菜、置信度越界、负数、NaN/字符串、超长数组均有确定行为；确认前不写 Store，确认后仅保存快照和必要来源元数据，不保存原图/base64。

## 10. P2：API 代理与安全

### 10.1 必要性

当前 `VITE_VISION_API_KEY` 会被 Vite 注入浏览器产物，任何访问者都能读取。它只适合个人本地开发，**不能作为生产秘密**。公开部署前必须把供应商密钥移到服务端环境变量，浏览器只调用 FitTrack 代理。

### 10.2 最小接口

`POST /v1/food-recognition`

选择 `multipart/form-data`，字段名 `image`。理由：避免 base64 约 33% 体积膨胀，浏览器与 `PhotosPicker` 数据都可直接上传；元数据可使用普通字段或单独 `options` JSON 字段。第一版不接受远程图片 URL，避免 SSRF。

请求：

```http
POST /v1/food-recognition HTTP/1.1
Content-Type: multipart/form-data; boundary=...
X-Request-Id: optional-client-id

image=<jpeg-or-png-binary>
locale=zh-CN
```

成功响应：

```json
{
  "requestId": "rec_01H...",
  "items": [
    {
      "name": "鸡胸肉",
      "amountG": 150,
      "amountRangeG": { "min": 110, "max": 200 },
      "kcal": 248,
      "kcalRange": { "min": 180, "max": 350 },
      "protein": 46.5,
      "carb": 0,
      "fat": 5.4,
      "confidence": 0.68,
      "uncertaintyReasons": ["厚度不可见", "烹调用油未知"],
      "matchedFoodId": null
    }
  ],
  "warnings": ["结果为估算，请确认份量与烹调用油"]
}
```

错误响应统一：

```json
{
  "error": {
    "code": "RATE_LIMITED",
    "message": "请求过于频繁，请稍后重试",
    "requestId": "rec_01H...",
    "retryAfterSeconds": 30
  }
}
```

| HTTP | code | 含义 |
|---|---|---|
| 400 | `INVALID_REQUEST` | 缺文件或字段错误 |
| 413 | `IMAGE_TOO_LARGE` | 压缩后仍超过限制 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | MIME/文件签名不支持 |
| 422 | `NO_FOOD_FOUND` / `INVALID_MODEL_RESPONSE` | 无食物或模型响应不合约 |
| 429 | `RATE_LIMITED` | 用户/IP/部署额度限流 |
| 502 | `UPSTREAM_ERROR` | 供应商失败 |
| 504 | `UPSTREAM_TIMEOUT` | 供应商超时 |
| 503 | `FEATURE_DISABLED` | 视觉服务关闭或预算熔断 |

### 10.3 限制、安全与隐私

- 客户端仍压缩到最长边 1280、JPEG 0.82；服务端硬限制建议 5 MiB、最多 1 张；实际解码后再限制像素数，防压缩炸弹。
- 允许 `image/jpeg`、`image/png`；校验 MIME 与魔数，拒绝 SVG、HEIC（第一版由客户端转换）、任意文件。
- 上游总超时建议 20 秒；客户端 25 秒。超时不自动重复扣费。
- 按匿名会话/IP 做短窗限流，并设置部署级每日预算、单请求 token 上限、最大响应 items 数；生产若有账号再叠加用户维度。
- 供应商 API key 仅存在服务端秘密管理，不下发、不回显、不进入前端 source map。
- CORS 仅允许配置的 Web origin allowlist，不使用 `*`；Apple 原生客户端不依赖浏览器 CORS，但仍需服务鉴权/滥用控制。
- 不记录原图、base64、完整 multipart、供应商 key或用户营养明细。请求处理完成立即释放内存；日志只保留 requestId、耗时、状态码、供应商类别、items 数、估算成本。
- 错误日志脱敏：不写文件名、用户输入名称和供应商原始响应正文；原始响应仅在内存校验。
- 隐私提示明确：图片会临时发送至配置的第三方模型提供商用于识别，但 FitTrack 不保存原图；上线前核对提供商数据保留政策。

### 10.4 配置

**本地开发**可选：

- `VISION_PROXY_URL=http://localhost:...`，服务端读取 `VISION_API_KEY/API_URL/MODEL`；或
- 保留当前浏览器直连作为仅开发模式，必须有醒目标记，且构建生产包时检测到 `VITE_VISION_API_KEY` 即失败。

**生产**：前端仅配置公开的 `VITE_VISION_PROXY_URL`；秘密使用部署平台服务端环境变量。`VITE_*` 的任何值都应视为公开配置，不能存生产 key。

### 10.5 可观测性与验收

指标：请求量、成功率、P50/P95 延迟、400/413/415/422/429/5xx、上游失败率、平均 items、估算 token/成本、预算熔断次数。不得以图片或食物名作为 metric label。

验收包括 CORS 拒绝非 allowlist、超限、伪造 MIME、超时、限流、供应商 key 不出现在 JS 产物/响应/日志、请求完成后无原图持久化。

## 11. P2：Mac/iOS 图片识别

### 11.1 范围与平台边界

- 共用 SwiftUI 页面逻辑，使用 `PhotosPicker` 选择相册图片；macOS 与 iOS 17 均验证可用性。
- 第一版不加入 iOS 相机，不增加 `NSCameraUsageDescription`，避免把相机权限和设备差异混入首版。
- iOS 当前仅保证构建，因此必须在至少一台真机验证相册选择、内存、旋转方向、上传取消和前后台切换。

### 11.2 压缩和 DTO

读取 `PhotosPickerItem` 后：

1. 限制输入体积并异步解码；
2. 应用 EXIF 方向，生成方向正确的位图；
3. 保持宽高比缩放，最长边 1280；
4. 输出 JPEG 质量约 0.82；透明 PNG 可铺白底；
5. 只在内存或系统临时目录短暂存在，上传完成/取消后删除，不写入 FitTrack JSON。

Apple 端复用第 10 节代理响应 DTO 与错误码，不直接解析供应商专有 `choices`。`VisionRecognitionService` 负责 multipart、超时、取消和解码；UI 只处理草稿与确认。

### 11.3 UI、Store、测试与验收

- 选择图片 → 本地预览 → 识别 → 多条草稿编辑 → 用户确认 → Store 批量写入。
- 低置信度、范围、误差原因与 Web 同口径；离线时禁用识别但保留手动记录。
- 确认后不保存原图；可选 `imageName` 仅是显示元数据，建议新实现不再依赖它。
- 测试旋转照片、超大图、PNG 透明图、取消选择、重复点击、网络切换、后台返回、低内存、代理各种错误。

验收要求 Mac 和 iOS DTO fixture 解码一致；iOS 真机完成一次完整识别确认；App 沙盒和导出 JSON 中不存在原图/base64。

## 12. P3：跨设备同步的接口与前置约束

完整选型和推荐路径见 [`docs/数据同步方案.md`](./数据同步方案.md)，本文不重复 Gist/Worker 等比较。饮食系统只定义以下前置条件：

1. 所有可同步实体有稳定 id；
2. `dietLogs`、`workouts`、`bodyMetrics`、`plannedWorkouts`、`mealTemplates` 等按 id 合并；
3. 若实体只增不改，可取 id 并集；但本方案加入日志编辑后，必须增加 `updatedAt` 与 `deletedAt` 或独立墓碑。否则“只增不改并集”立即失效：旧副本会覆盖编辑，删除项会复活；
4. 同 id 比较 `updatedAt`，较新版本胜；时间相同但内容不同必须报告冲突，不能静默任选；
5. 删除用墓碑传播，保留期覆盖最长离线周期后才可压缩；
6. 单值配置需 `updatedAt` 或显式选择；同步前创建本地快照；
7. 本地永远可离线使用，同步是显式动作，失败不回滚本地刚记录的数据。

建议同步层接口：

```text
loadLocalEnvelope() -> SyncEnvelope
fetchRemoteEnvelope() -> SyncEnvelope
merge(local, remote) -> MergeResult
preview(result) -> counts/conflicts
commitLocal(result) + pushRemote(result)
```

跨端必须共享 merge fixtures，包括：新增、同 id 新旧版本、墓碑、时钟相同冲突、旧客户端缺时间戳。缺 `updatedAt` 的旧实体应视为最早版本，但第一次迁移必须为本地实体补稳定时间戳或记录迁移基线，避免每次重写。

}

## 15. 状态机、错误处理与可观测性

### 15.1 视觉识别状态机

```text
idle
  → selecting
  → compressing
  → uploading
  → reviewing
  → saving
  → success

selecting/compressing/uploading → failed → retry 或回到 idle
reviewing → cancelled → idle
```

同一时刻只允许一个活动请求；选择新图应取消旧请求并丢弃旧响应。用 requestId 防止慢响应覆盖新图片草稿。

### 15.2 校准建议状态机

```text
insufficient → withinRange 或 deviating
第一次同向 deviating → 等待下一次合格评估
连续第二次同向 deviating → suggested
suggested → accepted 或 dismissed
目标改变/方向反转 → 连续计数重置
```

已接受/忽略的评估不可再次决定。算法升级后不重写历史决定；新评估保存算法版本（可在实现时加 optional `algorithmVersion`）。

### 15.3 通用错误处理

- 持久化失败必须提示“本次改动可能未保存”，不能只吞异常；Web 当前写 localStorage 失败静默，P0 应补可观察状态。
- 批量操作先在内存完成校验，再单次 commit；不得逐条保存造成半成功。
- 导入、迁移和同步先验证后提交，失败保留原数据和恢复快照。
- 对用户显示可操作信息；技术细节与 requestId 可复制，但不暴露 key、供应商响应或本地路径。

### 15.4 可观测性

本地功能记录匿名计数即可：迁移版本、导入成功/失败原因类别、评估是否数据不足；若无遥测基础设施，则只保留本地诊断，不为此新增后端。外部代理按第 10.5 节采集聚合指标。任何日志不得包含原图、完整饮食明细、体重序列或秘密。

### 17.2 数据备份与回滚

- 每次 schema 迁移、完整恢复和首次同步前自动保存带时间戳快照；Web 应触发用户下载或在受控本地备份槽保存并提供导出，不能假设 localStorage 永久可靠。

- 算法回滚只停止产生新建议，不撤销用户已接受的历史校准；可提供“将校准归零”的显式操作并记录决定。

## 19. 医疗与营养边界

FitTrack 提供的是一般性健身与饮食记录/估算，不是医疗建议，也不用于诊断、治疗或替代医生、注册营养师意见。

以下情况不应提供激进自动建议，程序应停止方向性校准并提示咨询专业人士：

- 计算结果触及极端低热量或持续接近 `1200 kcal` 下限；下限不是对所有人的医学安全保证；
- 未成年人；
- 孕期或哺乳期；
- 已知或疑似进食障碍、快速体重变化、长期头晕乏力等风险信号；
- 需要疾病相关饮食管理（如糖尿病、肾病、肝病）或正在使用影响体重/食欲的药物；
- 用户资料或趋势出现明显异常、数据不足或互相矛盾。

应用不应通过文案鼓励补偿性节食、因单日超标惩罚性减餐或无监督快速增减重。自适应建议必须强调水分波动和数据局限，并始终允许忽略。

## 20. Definition of Done

一个阶段只有在以下条件全部满足时才算完成：

- 当前实现与规划状态在 UI/文档中没有混淆；
- 数据模型两端兼容，旧备份迁移与新备份 round-trip 通过；
- 核心计算为纯函数并有边界测试，跨端 oracle 无差异；
- Store 写入原子、失败可见、批量操作无半成功；
- 空态、缺失、异常、跨时区和取消路径有明确行为；
- 用户可在写入前预览外部识别或算法建议，且需明确确认；
- Web `npm test`、`npm run build`、`npm run lint` 通过；macOS/iOS 构建通过；需要真机的能力完成真机验收；
- 发布前备份、回滚路径和隐私提示已验证；
- 没有生产秘密进入 Web 产物、日志或响应；
- 验收标准有可复现证据，而不只是“页面能打开”。

## 21. 开放决策

实施前需逐项定案，不应在编码中隐式决定：

1. 完整恢复 UI 是否同时提供“全量替换”和“按 id 合并”，以及单值配置冲突交互；
2. `DietDayStatus.localDate` 是否固定 `YYYY-MM-DD`，跨时区旅行时是否保持记录地日期；推荐保持创建时本地日期并展示时区语义；
3. 宏量达标容差是否采用本文建议值；
4. 校准累计值在目标类型改变时归零还是保留为历史但停止生效；推荐归零生效值、保留历史；
5. 评估历史保留上限及归档策略；
6. 自定义食物是否用 `isCustom?: Bool` 标记，或把种子/用户食物统一处理；
7. API 代理运行平台、客户端鉴权和匿名滥用控制方式；
8. Vision 供应商的数据保留政策是否满足隐私要求；
9. 同步选型继续按 `docs/数据同步方案.md` 决策，及墓碑保留周期；
10. 营养高风险人群采用自我声明、年龄字段判断还是仅通用警示。任何方案都不能假装完成医学筛查。
